# 全量 corpus 的 review 与抽检计划

本计划用于 `outputs/corpus-fast-v1` 的 staging 验收。全量合并和导出完整性验证已经完成，两个审核工具已经实现；尚未启动正式 API 审核。旧版 `corpus-parallel-v1` 与中间 worker 已清理。

## 目标与启动条件

先全量处理已经隔离的 review 文本块，再用有限的分层样本检查保留文本、换行恢复和排除规则。DeepSeek 提供判断建议，核对原文后才形成可应用的决定。不得润色、补写、翻译原文，不因商业话题或教育价值低而直接删除自然日语。

启动时确认：

- 合并进程成功退出，`manifest.json` 的 `status` 为 `complete`；文件正在增长或仅目录存在都不表示完成。
- `document_origins` 与输入计划中的 2,289,346 条来源记录相符。
- 记录实际 keep/drop/review、片段、来源、split 和标注匹配计数；未匹配标注必须为零。
- 保留本版 manifest 的哈希，后续抽样和报告绑定该版本。抽检期间 corpus 只读。

## A：全量 review

读取合并后的 `review_blocks.jsonl`，按文档哈希、块 ID、文本快照和原因合并重复目标，保留所有来源与审计记录引用。计数单位为文本块，不是文档或请求。

每个案例附带原文位置、前后各约两行及相关处理结果；若证据不足，扩展局部上下文。模型返回“确定噪声”“自然文本但被规则隔离”“无法确认”及中文理由。无依据不恢复；无法确认的块继续隔离，单独统计，不阻止其他语料推进。

当前 builder 禁止用 keep 标注恢复规则已经 drop/review 的块，因此不能把模型的 keep 建议直接写进台账。确需恢复时，应先设计可追踪的精确修复/规则例外，记录原始与修复快照，并验证相关段落和分句结果。无法可靠恢复的块可以保持隔离。

## B：分层抽检，目标上限约 700 个不同案例

| 层 | 目标数 | 检查内容 |
| --- | ---: | --- |
| 保留文本 | 300 | 九个 FineWeb shard 各随机 30 条，Tatoeba 随机 30 条；检查自然性、网页残留、完整性 |
| 已合并的换行 | 100 | 按合并理由覆盖，核对是否错误连接标题、列表或独立句子 |
| 未合并的可疑边界 | 100 | 检查一句话/词是否仍被断开，平假名开头等只用于选样，不直接判合并 |
| 被排除的 fragments | 100 | 约 60 条无终止标点、20 条未闭括号、20 条异常闭括号；检查误排除 |
| 明确 drop 的块 | 50 | 覆盖 URL、装饰、空白/控制字符，检查是否误删正文 |
| 特殊与较长文本 | 50 | 覆盖长句、Latin/数字混排、括号/引号、多行列表附近文本 |

固定种子 42，按稳定顺序做蓄水池或哈希抽样，记录每层可用总体、实际样本数和不足原因。每层尽量每文档一个案例；重叠案例保留多层标签、只发送一次。按层抽样不是全库均匀抽样，不能把所有层的 issue 比例当作全库坏数据率；保留文本也应分来源/shard 报告，若汇总则按该层实际总体加权。

用于调整规则的抽检案例只从 train 文档组及最终 train 语料中选取。全量 review 如涉及 validation/test，其已检查并用于修改的文档组在新版本中归入 train，并处理相同句子在其他组的出现位置；无法完成隔离时，暂不恢复它们。最终 test 不参与反复调规则。

## 取样与 API 执行

- 不复用旧的 `prepare_recovery_audit.py` 全量读入方式：它面向小规模诊断，且部分逻辑没有重放当前全部批准标注。
- 新准备器基于最终 train JSONL、SQLite、审计文件和实际 spans 重建处理结果；限定内存，按 JSONL 字节范围并行选样、按来源文件并行取原文。只对选中文档重放同版规则与批准标注。
- 漏合并检查先从无标点且无旗标的 fragments 中抽取有限文档池，再验证实际相邻边界；属于两阶段诊断，不对全库所有未合并边界作均匀抽样。每层按文档哈希选样，不能直接估计全库句子坏数据率。
- 完整扫描只读、流式；避免逐案例重读全部 shard。抽中的原文按文件/row group 合并读取，核对文档哈希。
- 每请求约 5～10 个带上下文的案例，按估算 token 预算动态拆批，不机械固定条数。
- API 初始 3 个并发请求，共享一个限流器，最多 8 次/分钟、约 80,000 tokens/分钟，给学校 10 RPM / 100,000 TPM 限额留余量。其他程序使用同一账号时共同扣除额度。
- 保存每次原始回复、请求材料、使用量与解析结果；API key 仅从 `SJTU_API_KEY` 读取，不写入材料或日志。
- 缓存键包含输入、提示、模型和端点。校验 ID 恰好覆盖、JSON 字段合法、输出未截断；失败不算完成，支持断点续跑和有界退避重试。
- 429 时降低发送速度或按服务端要求暂停；不通过多个 worker 各自限流来突破共享配额。

假设全量 review 不足 1,000 条，总案例上限约 1,700。按每批 10 条、8 RPM，单是请求配额下限约 22 分钟；批次缩小、接口延迟与重试都会增加时间。API 阶段先预留约 30～90 分钟，不含脚本实现和最终核对时间，并在前 5～10 批后用实际吞吐量更新估计。

## 核对与通过标准

我核对模型标为 issue/uncertain 的案例，并随机核对至少 30 个 ok 案例，避免把模型判断当成金标准。你可查看中文摘要与少数仍有歧义的原文，不必逐条阅读全部样本。

以下为第一轮工程验收阈值，不是全库质量证明：

- 所有入选案例完成审核，无 pending；API 失败重跑至完成。
- 全量 review 块均有处置状态，无法确认者保持隔离并计数，不强行恢复。
- 300 条保留文本中，核对后确定明显不适合训练的案例不超过约 2%（实际满 300 条时不超过 6 条），且没有未处理的系统性问题。
- 同一错误原因出现至少 3 个不同文档案例，或某来源明显集中出错时，先从相关层再抽约 200 个案例，确认影响范围；不因单个例子改全局规则。
- 超过暂定阈值时，针对问题修复并复检，不直接进入正式 tokenizer。高风险层分开报告，不与随机保留样本混算。
- 修改边界时检查完整前后链条，验证修复后没有产生新残句；不只批准局部一对行。

如第一轮通过，就停止扩大这一轮语义审查。若需要修复，保存明确的本地决定和证据，输出新的 corpus 版本，优先只重处理受影响文档；是否需要全量重建由实际规则变更范围决定，不能覆盖当前 staging。

## 交付与后续

已实现两个独立工具：`prepare_corpus_review.py`（流式分层抽样与材料生成）、`review_corpus_parallel.py`（统一限流的 API 并发审核）。现有脚本和合并任务保持可复现。命令与限制见 [工具使用说明](corpus-review.md)。本轮实现与本地验证不启动正式审核。

审核输出规划在 `outputs/corpus-review-v1/`：抽样 manifest、cases、原始 responses、缓存、results、issues、pending、按层统计和中文总结。保留 source、文档/文本哈希、原文位置、抽样层与修复证据。

review＋抽检通过只代表本轮语义及处理质量验收通过。近重复/跨 split 泄漏检查是独立的冻结步骤，当前 manifest 的 `near_duplicate_detection=false` 不能直接改成已通过。完成必要的泄漏检查和修复、记录版本后，再冻结正式 corpus、训练正式 SentencePiece、生成 token 文件。不会因为抽检就把全量语料的 `lm_reviewed` 改为 true。

# zh-800m 第二版架构（arch2）设计

本文设计 800M 中文桌面模型的第二版架构，内部代号 `zh800m-arch2`。正在训练的 800M（[训练计划](training-zh-800m-plan.md)，下文称 arch1）不受影响。arch2 暂不开工，等 arch1 训完并评测后再排期。

## 为什么要改

arch1 用 [8903f17](../../src/vimeml/training/joint_zh200m.py) 的打包代码训练，`lm_microbatch` 64。正式训练到 25% 时实测：

- 墙钟约 0.182 秒一步，其中纯计算的中位数约 0.12 秒；每步约 10.6 万个监督 token；
- 1,198,964 次更新约 2.5 天；
- 按实测矩阵乘峰值算，有用 MFU 约 20%；
- 填充比约 1.37（冒烟实测）；
- `lm_microbatch` 128 的冒烟是 0.259 秒一步，loss 与 64 的差不超过 0.003%，所以正式训练选了 64。

目标：

- 参数仍约 800M，12K 词表不变，数据、数据顺序与 token 预算不变；
- 每次更新的批量加大到 arch1 的 k 倍（k 由 200M 前置检查定，候选 4 或 8，见「加大批量」）；
- 同样的硬件上，一遍训练压到 1.5 天以内，相当于有用 MFU 30–40%；
- 质量不低于 arch1（判定规则见下）。

## 对集群方案的取舍

集群提出了 arch2 的需求：序列打包加长上下文、RoPE、GQA、可选 QK-norm，以及四个候选形状。本设计的取舍如下。

| 提议 | 取舍 | 理由 |
| --- | --- | --- |
| 序列打包 | **采纳，但按窗口隔离** | 见下一节 |
| 按文档重建 c2048 窗口 | **不采纳** | 会改变训练数据的内容和分布，见下一节 |
| RoPE | 采纳 | 打包后每个窗口的位置都从 0 开始，RoPE 是相对位置，实现最自然。learned position 只有 0.8M 参数，省参数不是理由 |
| GQA，8 个 KV 头 | 采纳，改为 7 个 KV 头 | 见「架构」一节 |
| QK-norm | 采纳 | 保持 3e-4 的峰值学习率时更稳 |
| 形状 B2（d1792 / 23 层） | 采纳，KV 头改为 7 个 | 23 层比 27 层少 15% 的串行层；宽高比在常见范围内；28 个 Q 头分不成 8 组，见「架构」 |
| `lm_batch` 改按 token 计 | 不采纳 | 仍按窗口计，改为 2048 × k 个窗口；数据顺序和 loss 归一化与 arch1 相同，见「加大批量」 |

### 打包只按窗口隔离，不做文档级长上下文

- arch1 的窗口按段落切分，平均约 34–42 个 token（[训练计划](training-zh-800m-plan.md)「形状」一节）。按文档重建 c2048 窗口，模型就会学跨段落的长上下文。这改变了训练分布，也违反「不改数据内容」的约束。
- 输入法用到的上下文很短：输入框内的上下文加上拼音。800M 按段落窗口训练，正好对得上这种用法。它还是 20M 第四轮蒸馏的老师，老师看到的输入和学生一样短。
- 按文档重建还要重做窗口索引和混合数据，钉新的 `dataset_sha256`，步数也跟着变。这样 arch2 就不能和 arch1 在同样的 token 上直接比较。
- 速度的收益来自打包本身，不来自跨窗口注意力。把多个窗口拼进一行，每个窗口是一个独立段：位置从 0 开始，注意力只在段内按因果方向看（块对角因果 mask）。这样训练目标与 arch1 逐 token 相同。

### 瓶颈先测清楚，再动架构

集群的诊断是「序列太短，矩阵乘吃不饱」。这一点只对了一半：

- 矩阵乘的 M 维是一个微批里所有位置的总数，现在每个微批有几万个位置，与单行长短无关。行短的代价在于填充、长度很短的注意力核，以及每次前向/反向的固定开销。
- arch2 与 arch1 的参数量几乎相同（7.77 亿对 7.84 亿），所以每步梯度 all-reduce 的量也相同，FP32 约 3.1 GB。如果一步里大部分时间花在通信或主机同步上，换架构达不到 1.5 天。

按每卡约 2 万个填充位置估算，理论计算只要约 60 毫秒一步。实测的 0.182 秒分成两块：

- 约 60 毫秒花在计算之外：通信、同步、主机端；
- 计算本身约 0.12 秒，是理论值的两倍：短注意力核、填充、kernel 发射。

两块都要先找到具体去向，所以开工前先做第 0 步。

## 第 0 步：定位瓶颈（在 arch1 代码上做，不训练）

1. **单进程对照**：用单卡跑与多卡时每卡相同的负载（同样的行数和长度），对比单步耗时。两者之差就是通信和同步的成本。
2. **all-reduce 带宽**：在训练环境里对 3.1 GB 的 FP32 张量做 all-reduce，测有效带宽。打开 NCCL 的 INFO 日志，确认走的是卡间直连，而不是共享内存或网络套接字。
3. **profiler**：用 `torch.profiler` 在 rank 0 上抓 5 步，拆分计算、通信、空闲和主机端（打包、collate、`.item()` 同步）各占多少。

判定：

- 通信超过一步的 30%：先处理通信，再上 arch2。办法有三种：
  - 只有一个微批时让 all-reduce 与反向重叠；
  - 调整 DDP 的 bucket；
  - 必要时用 BF16 梯度通信。这会改变梯度的舍入，要记入偏离。
- 主机端超过 15%：把打包移到 DataLoader 的 worker 里，每步只做一次合并的同步。
- 第 0 步的结论写成报告，决定执行层的改动范围。

## 架构

| 项 | arch1 | arch2（冻结） |
| --- | --- | --- |
| 词表 | 12,288 | 12,288（不变，与 20M 蒸馏对齐） |
| d_model | 1536 | 1792 |
| 层数 | 27 | 23 |
| 注意力 | 24 头 × 64 | Q 28 头 × 64，KV 7 头 × 64（GQA，每组 4 个 Q 头） |
| SwiGLU d_ff | 4096 | 4608 |
| 归一化 | RMSNorm，pre-norm | RMSNorm，pre-norm；Q、K 各加一层逐头 RMSNorm（QK-norm） |
| 位置 | learned，512 | RoPE，θ = 10000，作用于全部 64 维 |
| 段长上限 | 512 | 512（单个窗口，与 arch1 相同） |
| 训练行长 | 按窗口补齐 | 2048，多个窗口打包 |
| bias / 共享嵌入 | 无 / 共享 | 无 / 共享 |
| 参数 | 784,157,184 | **776,524,928** |
| 训练 FLOP / token | 约 4.7 GFLOP | 约 4.66 GFLOP |

- **KV 头数**：集群的 B2 写的是 28 个 Q 头配 8 个 KV 头。28 不能被 8 整除，GQA 分不成整组，所以改成 7 个 KV 头。
  - 另一种做法是 8 个 KV 头配 32 头 × 56 维。head_dim 56 不是 64 的倍数，注意力核的效率差，不采用。
  - 4 个 KV 头（每组 7 个）会把 KV 压得过狠；14 个则收益减半。
- **每层参数**：Q 和 O 投影各 1792 × 1792，K 和 V 投影各 1792 × 448，SwiGLU 3 × 1792 × 4608，再加两层 RMSNorm 和两组 64 维 QK-norm 权重。
- **总参数** = 12,288 × 1792（共享嵌入）+ 23 × 每层 + 1792（末层 norm）。
- **FLOP**：按 6N 计。窗口平均约 40 个 token，注意力的二次项可以忽略。

**GQA 的实际收益**

- 每个 token 的 KV cache 从 27 × 2 × 1536 = 82,944 个值降到 23 × 2 × 7 × 64 = 20,608 个，约为原来的 1/4。
- 桌面端在短上下文上解码，每步主要是读一遍权重（约 1.56 GB，BF16），所以单句延迟不会因此快几倍。
- 收益主要在束搜索：束宽 16、多桶并行时，KV 的显存和读写量明显下降。
- 实际延迟仍按发布门槛在 Mac 上实测。

## 执行层

- **打包**：
  - 每次更新的 2048 × k 个 LM 窗口和 384 × k 条拼音样例，按长度从长到短，用 first-fit 装进长 2048 的行。每个窗口或样例是一个段。
  - 注意力用 `torch.nn.attention.flex_attention`，按段号生成块对角因果 mask；RoPE 的位置按段重置。
  - 损失和 `per_kind` 权重沿用 arch1：每个 token 的权重是「它所属任务的权重 ÷ 该任务的全局监督 token 数」。
- **形状**：行宽固定 2048，只有行数可变。编译时只把 batch 维标为动态，行数至少为 2，避免重编译。
- **微批预算**：行数 × 2048 ≤ `lm_microbatch` × 512。`lm_microbatch` 从 64（每微批 16 行）开始，按冒烟的单步耗时选，不按显存取最大值：arch1 实测 64 比 128 快。k 倍批量下每步约 40–80 万个 token，每卡要做几次前向/反向；除最后一个微批外都在 `no_sync` 下累积梯度，每步只做一次 all-reduce。
- **数据并行按 token 均衡**：段按 token 数分给各 rank（贪心），不再按行连续切分。归一化仍用全局 token 数，梯度之和不变。
- **同步**：每步只做一次合并同步（各任务 loss 之和、梯度范数、停止标志），不再逐项做 `.item()`。
- **验证、推理和导出**都不打包：沿用逐窗口的普通前向和 KV cache 路径。

## 更多加速手段

前四项只改执行方式，训练目标不变。收益最大的是加大批量，它改配方，单独成节（见「加大批量」）。

1. **去掉每步的主机同步，让 CPU 提前准备下一步。**
   - 现在每步有四处让 CPU 等 GPU 的地方：
     - 计时用的 `torch.cuda.synchronize`；
     - 各任务 loss 的 `.tolist()`，连同它的 all-reduce；
     - `float(clip_grad_norm_)`；
     - 每步一次的停止标志 all-reduce（`ctx.any`）。
   - 后果是下一步的打包、collate、拷贝和 kernel 发射都只能等这一步算完再开始。
   - 改法：
     - 计时改用 CUDA event，在日志间隔统一读取；
     - loss 之和与梯度范数留在 GPU 上累加，到日志间隔再取；
     - 停止标志每 10 步检查一次，仍保证所有 rank 在同一次更新后停下；
     - 梯度非有限时，在 GPU 上跳过这一步（fused AdamW 支持 GradScaler 用的 `found_inf` 机制），并在下一次日志检查时报错退出。这用到 PyTorch 的内部接口，要有单测覆盖。
2. **CUDA Graphs。**
   - 在打包的基础上，把每个微批固定成 R 行 × 2048。行数不够时补空行；每步的段数可变，就填进固定长度的段号张量里。
   - 用 `torch.compile(mode="reduce-overhead")` 把前向和反向录成图，每步只重放，kernel 发射开销几乎归零。
   - 第 0 步的 profiler 显示发射或调度开销明显时再做。
3. **通信与计算重叠。**
   - 每步只在最后一个微批的反向里同步梯度，DDP 在这次反向过程中按 bucket 发 all-reduce。
   - 打开 `gradient_as_bucket_view`；计算图固定时打开 `static_graph`；按 profiler 结果调 `bucket_cap_mb`。
4. **GEMM 调优。**
   - `torch.compile` 用 `max-autotune-no-cudagraphs`（和第 2 项一起用时用 `max-autotune`），让 GEMM 选更合适的分块。
   - 交叉熵改成分块融合实现，省掉完整 logits 的显存往返。收益小，主要是为了给更大的微批腾显存。
**不做**：

- FP8 及其他低于 BF16 的矩阵乘：禁止使用，任何一项都不引入。
- 加卡：全局批量固定时，每卡的计算随卡数减少，每步的通信和同步却不减，加卡几乎不提速。
- 激活重算：显存很宽裕，重算只会更慢。

## 加大批量（采纳）

arch1 每步只有约 10 万个 token（约 7.9 万 LM 监督 token 加拼音）。对 800M 来说这个批量很小，同量级的公开模型一般用 50 万到 200 万个 token 一步。每步的固定成本（约 3.1 GB 的 all-reduce、优化器、同步）不随批量变化，批量加大 k 倍，这些成本按 token 摊薄到 1/k。arch2 采用 k 倍批量，k 取 4 或 8，由下面的前置检查决定。

### 配方随 k 的换算

| 项 | arch1 | arch2（k 倍） | k = 4 | k = 8 |
| --- | --- | --- | --- | --- |
| `lm_batch`（窗口） | 2048 | 2048 × k | 8192 | 16384 |
| 拼音配比 full/mixed/initials/error | 96/128/112/48 | 各 × k | 384/512/448/192 | 768/1024/896/384 |
| 每步 token（约） | 10 万 | 10 万 × k | 40 万 | 80 万 |
| 更新次数 | 1,198,964 | 1,198,964 ÷ k（dry-run 实测） | 约 299,741 | 约 149,871 |
| 峰值学习率 | 3e-4 | 3e-4 × √k | 6e-4 | 8.5e-4 |
| 末学习率 | 3e-5 | 峰值 ÷ 10 | 6e-5 | 8.5e-5 |
| warmup（步） | 2000 | 2000 ÷ k（token 数不变） | 500 | 250 |
| `bucket_multiplier` | 64 | 64 ÷ k | 16 | 8 |
| 测点 | 20 个 | 20 个，按 token 数对齐 | | |

- **数据顺序**：`bucket_multiplier` 改为 64 ÷ k 后，长度池仍是 131,072 个窗口，池的序列与 arch1 完全相同。池内按长度切成 k 倍大的批，再打乱批的顺序，所以每个大批相当于 arch1 同一个池里长度相邻的 k 个批。
- **拼音遍数不变**：配比与 LM 批量同乘 k，更新次数除以 k，四类拼音仍各过 1.42/1.35/1.38/1.75 遍。
- **不变的项**：AdamW（β 0.9/0.95，wd 0.1）、梯度裁剪 1.0、seed、`per_kind` 归一化、余弦调度的形状。
- **学习率**：平方根规则是 AdamW 下的常用起点。arch2 有 QK-norm，对较高的学习率更稳。前置检查同时验证这个换算。

### 前置检查（200M，在 arch2 开工前做）

用 12K 联合拼音 200M 的配方（`configs/train-zh200m-12k-pinyin-pt.toml`）跑三臂。每臂都是一条完整的短余弦调度，token 预算相同，都是 200M 全程的 10%：

| 臂 | `lm_batch` | 拼音配比 | 更新次数（约） | 峰值 → 末学习率 | warmup | `bucket_multiplier` |
| --- | ---: | --- | ---: | --- | ---: | ---: |
| 1× | 512 | 48/64/56/24 | 84,500 | 6e-4 → 6e-5 | 1000 | 64 |
| 4× | 2048 | 192/256/224/96 | 21,125 | 1.2e-3 → 1.2e-4 | 250 | 16 |
| 8× | 4096 | 384/512/448/192 | 10,563 | 1.7e-3 → 1.7e-4 | 125 | 8 |

- 三臂的数据、顺序和 seed 相同，更新次数以 dry-run 为准。
- 比较训练末的 web BPC 和四类拼音验证 loss，以及同 token 数的测点曲线。
- **判定**：取通过的最大 k。通过条件是 web BPC 比 1× 臂高不超过 0.01，且四类拼音验证 loss 都比 1× 臂高不超过 0.01；训练中出现 loss 尖峰（比前 1000 步均值高 0.5 以上）也算不通过。
- 8× 不通过而 4× 通过，用 4×；4× 也不通过，加跑 2× 臂（1024 窗口，学习率 8.5e-4）再定。
- 前置检查作为集群作业运行，结果写成报告后再冻结 arch2 的配方。
- 配置：`configs/train-zh200m-batch-precheck-{1x,4x,8x}.toml`。`budget_fraction = 0.1` 把前 10% 的更新作为一次完整训练（余弦、预热和里程碑都按缩短后的长度）；`lm_microbatch = 512` 让 4× 和 8× 的批次在每张卡上分 4 段和 8 段前向，梯度不变。

### 速度预期

批量加大后每步的计算按 k 倍增长，固定成本不变。按 arch1 实测（每步约 0.12 秒计算、约 60 毫秒其他开销）粗算：

- 只加大批量：k = 4 时一遍约 1.9 天，k = 8 时约 1.8 天。省下的只是计算之外的那部分时间，k 再大收益也有限。
- 要到 1.5 天，计算本身还要提速约两成。这要靠打包（填充比从 1.37 降到 1.1 以下）、更大的 GEMM 形状和前四项加速。

验收门槛按 k 换算，见「开训前的验收」。

## 推理与导出要跟着改

- 模型：新增 `model_zh800m_arch2`，包含 RoPE、GQA、QK-norm、打包训练前向（段号输入）、普通前向和 `forward_cached`。
- 评测：`zh_torch_backend`、`zh13_lm_scores`、拼音生成（`pinyin_gen_zh.py`）和 Standard 都要能加载 arch2。
- 蒸馏：`joint_zh_pinyin` 的老师加载支持 arch2（同一 12K 词表，token 级 logits 直接对齐）。
- 桌面导出：Core ML 包补上 RoPE、GQA 和 QK-norm，数值语义与 PyTorch 前向对齐。

## 数据与配方

与 arch1 相同的项：

- 混合数据 `zh800m-12k-c512`，`dataset_sha256` 不变，不重建窗口；
- 拼音 store `zh-pinyin-pt-12k`，`per_kind` 归一化，各类拼音的遍数；
- 长度池的序列（见「加大批量」）和总 token 数；
- AdamW（β 0.9/0.95，wd 0.1），梯度裁剪 1.0，seed；
- 20 个测点（按 token 数对齐）和检查点保留规则。

与 arch1 不同的项：`[model]` 一节、模型代码、执行层，以及按 k 换算的批量、拼音配比、学习率、warmup、更新次数和 `bucket_multiplier`。arch2 与 arch1 在同样 token 数的测点上比较 web/chat/probe BPC。检查点间隔按 token 数保持不变，即步数除以 k。

## 开训前的验收

1. **单测**：
   - 参数量与形状；
   - GQA 分组与逐头复制等价；
   - RoPE 的 KV cache 解码与整段前向一致；
   - **打包等价**：同一批窗口，打包前向的逐 token loss 和梯度，与逐窗口单独前向一致（容差同 `tests/test_zh800m_pinyin.py`）；数据并行切分与单卡一致。
2. **dry-run**：参数 776,524,928；`max_steps` 约 1,198,964 ÷ k；拼音遍数与 arch1 相同（1.42/1.35/1.38/1.75）；plan 除模型、代码签名和「加大批量」表中的项外与 arch1 相同。
3. **20 步冒烟**，回报：
   - 稳态单步，目标不超过 0.11 × k 秒（k = 4 时 0.43 秒，k = 8 时 0.86 秒，即 1.5 天以内）；
   - `compiled_graphs`，以及第 1 步之后有没有超过 2 秒的步；
   - 峰值显存；
   - 填充比 `padded_positions ÷ (LM 输入 token + 拼音输入 token)`，目标不超过 1.1；
   - 第 20 步 loss，只做合理性检查。
4. **继续条件**：单步不超过 0.144 × k 秒（k = 4 时 0.58 秒，k = 8 时 1.15 秒，即 2 天以内，比 arch1 的 2.5 天至少快 20%）才开正式训练；否则带着 profiler 结果回来再定。

## 质量判定（预注册）

arch2 与 arch1 用同样的数据、同样的 token 数（批量和学习率按「加大批量」换算），在 development 上比较：

1. 主指标：公开拼音集自身重打分 Top-1（λ = 1.6），句子簇 sign-flip 配对检验。
2. arch2 取代 arch1 成为 800M 的条件（两条都要满足）：
   - 主指标不显著低于 arch1；
   - Standard 全拼重排的 Top-1 不显著低于 arch1。
3. 联想（轨道 A–D）和各测点 BPC 是描述性的。
4. 第四轮蒸馏用两者中主指标更高的一个当老师。

## 实现情况（2026-11-19）

已完成，有单元测试（`tests/test_zh800m_arch2.py`、`tests/test_zh_batch_precheck.py`）：

- `model_zh800m_arch2`：冻结的形状（776,524,928 参数，构造时检查）、RoPE、GQA（`enable_gqa`）、QK-norm；普通前向、打包前向（`segments`：每段位置从 0 开始，只在段内因果注意；CUDA 上用 flex_attention，其他设备用稠密掩码）和 `forward_cached`。测试：GQA 等于逐头复制；KV 路径与完整前向一致；打包后的 loss、梯度和 logits 与逐窗口单独前向一致；CUDA 上 flex 掩码与稠密掩码一致。
- 训练器：`joint_zh200m` 新增 stage `zh-800m-arch2`（每次更新 8192 或 16384 个窗口）。每张卡上所有任务的行按首次适配降序打包成 2048 token 的行，每次前向 `lm_microbatch × 512 ÷ 2048` 行；逐 token 权重和归一化与 arch1 相同，梯度与不打包的更新一致（有测试）。编译的隐藏层栈以位置和掩码为输入。
- 评测：搜索后端、Standard 打分、拼音生成、预测和蒸馏教师都通过 `zh_desktop` 加载 arch2 检查点。
- 配置：`configs/train-zh800m-arch2-k4.toml` 和 `-k8.toml`（只运行预检选中的那个），以及预检的三个 200M 配置。
- 第 0 步（`scripts/training/step0_zh800m.py`、`src/vimeml/training/step0_zh800m.py`）：`updates` 从随机权重出发，用训练器自己的更新循环跑若干次更新并逐次计时；可以数据并行运行，也可以用 `--emulate-world N` 在单进程里跑 N 卡运行中 rank 0 的那一份（单进程对照）。`--profile K` 把 rank 0 上 K 次更新的时间拆成计算、未被掩盖的通信、GPU 空闲和主机工作（等数据、打包、同步调用）。`allreduce` 测梯度大小的 FP32 all-reduce 带宽，分整块和 25 MB 分桶两种。arch2 的 20 步冒烟也用同一个 `updates` 命令计时。

尚未完成，都等第 0 步报告确定执行范围后再做：

- 数据并行按 token 数均衡（目前仍按连续行块分给各卡）；
- 去掉每次更新的主机同步、CUDA Graphs、通信重叠和 GEMM 调优（更多提速第 1–4 项）；
- arch2 的 Core ML 导出。

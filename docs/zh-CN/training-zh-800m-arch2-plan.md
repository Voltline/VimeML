# zh-800m 第二版架构（arch2）设计

本文设计 800M 中文桌面模型的第二版架构，内部代号 `zh800m-arch2`。正在训练的 800M（[训练计划](training-zh-800m-plan.md)，下文称 arch1）不受影响。arch2 暂不开工，等 arch1 训完并评测后再排期。

## 为什么要改

arch1 用 [8903f17](../../src/vimeml/training/joint_zh200m.py) 的打包代码训练，实测：

- 去掉首步编译后稳态约 0.26 秒一步，每步约 10.6 万个监督 token；
- 1,198,964 次更新约 3.6 天；
- 按实测矩阵乘峰值算，有用 MFU 约 14%；
- 填充比约 1.37。

目标：

- 参数仍约 800M，12K 词表不变，数据与 token 预算不变；
- 同样的硬件上，一遍训练压到 1.5 天以内，相当于有用 MFU 30–40%；
- 质量不低于 arch1（判定规则见下）。

## 对集群方案的取舍

集群提出了 arch2 的需求：序列打包加长上下文、RoPE、GQA、可选 QK-norm，以及四个候选形状。本设计的取舍如下。

| 提议 | 取舍 | 理由 |
| --- | --- | --- |
| 序列打包 | **采纳，但按窗口隔离** | 见下一节 |
| 按文档重建 c2048 窗口 | **不采纳** | 会改变训练数据的内容和分布，见下一节 |
| RoPE | 采纳 | 打包后每个窗口的位置都从 0 开始，RoPE 是相对位置，实现最自然。learned position 只有 0.8M 参数，省参数不是理由 |
| GQA，8 个 KV 头 | 采纳，改为 7 个 KV 头 | 见「架构」一节 |
| QK-norm | 采纳 | 保持 3e-4 的峰值学习率时更稳 |
| 形状 B2（d1792 / 23 层） | 采纳，KV 头改为 7 个 | 23 层比 27 层少 15% 的串行层；宽高比在常见范围内；28 个 Q 头分不成 8 组，见「架构」 |
| `lm_batch` 改按 token 计 | 不采纳 | 每次更新仍是 2048 个窗口，数据顺序、步数和归一化都与 arch1 相同 |

### 打包只按窗口隔离，不做文档级长上下文

- arch1 的窗口按段落切分，平均约 34–42 个 token（[训练计划](training-zh-800m-plan.md)「形状」一节）。按文档重建 c2048 窗口，模型就会学跨段落的长上下文。这改变了训练分布，也违反「不改数据内容」的约束。
- 输入法用到的上下文很短：输入框内的上下文加上拼音。800M 按段落窗口训练，正好对得上这种用法。它还是 20M 第四轮蒸馏的老师，老师看到的输入和学生一样短。
- 按文档重建还要重做窗口索引和混合数据，钉新的 `dataset_sha256`，步数也跟着变。这样 arch2 就不能和 arch1 在同样的 token 上直接比较。
- 速度的收益来自打包本身，不来自跨窗口注意力。把多个窗口拼进一行，每个窗口是一个独立段：位置从 0 开始，注意力只在段内按因果方向看（块对角因果 mask）。这样训练目标与 arch1 逐 token 相同。

### 瓶颈先测清楚，再动架构

集群的诊断是「序列太短，矩阵乘吃不饱」。这一点只对了一半：

- 矩阵乘的 M 维是一个微批里所有位置的总数，现在每个微批有几万个位置，与单行长短无关。行短的代价在于填充、长度很短的注意力核，以及每次前向/反向的固定开销。
- arch2 与 arch1 的参数量几乎相同（7.77 亿对 7.84 亿），所以每步梯度 all-reduce 的量也相同，FP32 约 3.1 GB。如果一步里大部分时间花在通信或主机同步上，换架构达不到 1.5 天。

按 0.26 秒一步、每卡约 2 万个填充位置估算，纯计算只要约 60 毫秒。剩下约 200 毫秒必须先找到去向。所以开工前先做第 0 步。

## 第 0 步：定位瓶颈（在 arch1 代码上做，不训练）

1. **单进程对照**：用单卡跑与多卡时每卡相同的负载（同样的行数和长度），对比单步耗时。两者之差就是通信和同步的成本。
2. **all-reduce 带宽**：在训练环境里对 3.1 GB 的 FP32 张量做 all-reduce，测有效带宽。打开 NCCL 的 INFO 日志，确认走的是卡间直连，而不是共享内存或网络套接字。
3. **profiler**：用 `torch.profiler` 在 rank 0 上抓 5 步，拆分计算、通信、空闲和主机端（打包、collate、`.item()` 同步）各占多少。

判定：

- 通信超过一步的 30%：先处理通信，再上 arch2。办法有三种：
  - 只有一个微批时让 all-reduce 与反向重叠；
  - 调整 DDP 的 bucket；
  - 必要时用 BF16 梯度通信。这会改变梯度的舍入，要记入偏离。
- 主机端超过 15%：把打包移到 DataLoader 的 worker 里，每步只做一次合并的同步。
- 第 0 步的结论写成报告，决定执行层的改动范围。

## 架构

| 项 | arch1 | arch2（冻结） |
| --- | --- | --- |
| 词表 | 12,288 | 12,288（不变，与 20M 蒸馏对齐） |
| d_model | 1536 | 1792 |
| 层数 | 27 | 23 |
| 注意力 | 24 头 × 64 | Q 28 头 × 64，KV 7 头 × 64（GQA，每组 4 个 Q 头） |
| SwiGLU d_ff | 4096 | 4608 |
| 归一化 | RMSNorm，pre-norm | RMSNorm，pre-norm；Q、K 各加一层逐头 RMSNorm（QK-norm） |
| 位置 | learned，512 | RoPE，θ = 10000，作用于全部 64 维 |
| 段长上限 | 512 | 512（单个窗口，与 arch1 相同） |
| 训练行长 | 按窗口补齐 | 2048，多个窗口打包 |
| bias / 共享嵌入 | 无 / 共享 | 无 / 共享 |
| 参数 | 784,157,184 | **776,524,928** |
| 训练 FLOP / token | 约 4.7 GFLOP | 约 4.66 GFLOP |

- **KV 头数**：集群的 B2 写的是 28 个 Q 头配 8 个 KV 头。28 不能被 8 整除，GQA 分不成整组，所以改成 7 个 KV 头。
  - 另一种做法是 8 个 KV 头配 32 头 × 56 维。head_dim 56 不是 64 的倍数，注意力核的效率差，不采用。
  - 4 个 KV 头（每组 7 个）会把 KV 压得过狠；14 个则收益减半。
- **每层参数**：Q 和 O 投影各 1792 × 1792，K 和 V 投影各 1792 × 448，SwiGLU 3 × 1792 × 4608，再加两层 RMSNorm 和两组 64 维 QK-norm 权重。
- **总参数** = 12,288 × 1792（共享嵌入）+ 23 × 每层 + 1792（末层 norm）。
- **FLOP**：按 6N 计。窗口平均约 40 个 token，注意力的二次项可以忽略。

**GQA 的实际收益**

- 每个 token 的 KV cache 从 27 × 2 × 1536 = 82,944 个值降到 23 × 2 × 7 × 64 = 20,608 个，约为原来的 1/4。
- 桌面端在短上下文上解码，每步主要是读一遍权重（约 1.56 GB，BF16），所以单句延迟不会因此快几倍。
- 收益主要在束搜索：束宽 16、多桶并行时，KV 的显存和读写量明显下降。
- 实际延迟仍按发布门槛在 Mac 上实测。

## 执行层

- **打包**：
  - 每次更新的 2048 个 LM 窗口和 384 条拼音样例，按长度从长到短，用 first-fit 装进长 2048 的行。每个窗口或样例是一个段。
  - 注意力用 `torch.nn.attention.flex_attention`，按段号生成块对角因果 mask；RoPE 的位置按段重置。
  - 损失和 `per_kind` 权重沿用 arch1：每个 token 的权重是「它所属任务的权重 ÷ 该任务的全局监督 token 数」。
- **形状**：行宽固定 2048，只有行数可变。编译时只把 batch 维标为动态，行数至少为 2，避免重编译。
- **微批预算不变**：行数 × 2048 ≤ `lm_microbatch` × 512。`lm_microbatch` 64 对应每微批 16 行。按每步约 10–12 万个 token 估算，每卡通常一次前向/反向就够。
- **数据并行按 token 均衡**：段按 token 数分给各 rank（贪心），不再按行连续切分。归一化仍用全局 token 数，梯度之和不变。
- **同步**：每步只做一次合并同步（各任务 loss 之和、梯度范数、停止标志），不再逐项做 `.item()`。
- **验证、推理和导出**都不打包：沿用逐窗口的普通前向和 KV cache 路径。

## 推理与导出要跟着改

- 模型：新增 `model_zh800m_arch2`，包含 RoPE、GQA、QK-norm、打包训练前向（段号输入）、普通前向和 `forward_cached`。
- 评测：`zh_torch_backend`、`zh13_lm_scores`、拼音生成（`pinyin_gen_zh.py`）和 Standard 都要能加载 arch2。
- 蒸馏：`joint_zh_pinyin` 的老师加载支持 arch2（同一 12K 词表，token 级 logits 直接对齐）。
- 桌面导出：Core ML 包补上 RoPE、GQA 和 QK-norm，数值语义与 PyTorch 前向对齐。

## 数据与配方（与 arch1 完全相同）

- 混合数据 `zh800m-12k-c512`，`dataset_sha256` 不变，不重建窗口；
- 拼音 store `zh-pinyin-pt-12k`，配比 96/128/112/48，`per_kind` 归一化；
- 每次更新 2048 个窗口，共 1,198,964 次更新，数据顺序与 arch1 相同；
- 峰值学习率 3e-4 → 3e-5，warmup 2000，AdamW（β 0.9/0.95，wd 0.1），梯度裁剪 1.0，seed 不变；
- 20 个测点、检查点间隔和保留规则不变。

只有 `[model]` 一节、模型代码和执行层改变。因为数据和顺序都相同，arch2 与 arch1 每个测点的 web/chat/probe BPC 可以直接对比。

## 开训前的验收

1. **单测**：
   - 参数量与形状；
   - GQA 分组与逐头复制等价；
   - RoPE 的 KV cache 解码与整段前向一致；
   - **打包等价**：同一批窗口，打包前向的逐 token loss 和梯度，与逐窗口单独前向一致（容差同 `tests/test_zh800m_pinyin.py`）；数据并行切分与单卡一致。
2. **dry-run**：参数 776,524,928；`max_steps` 1,198,964；拼音遍数与 arch1 相同（1.42/1.35/1.38/1.75）；plan 除模型和代码签名外与 arch1 相同。
3. **20 步冒烟**，回报：
   - 稳态单步，目标不超过 0.12 秒；
   - `compiled_graphs`，以及第 1 步之后有没有超过 2 秒的步；
   - 峰值显存；
   - 填充比 `padded_positions ÷ (LM 输入 token + 拼音输入 token)`，目标不超过 1.1；
   - 第 20 步 loss，只做合理性检查。
4. **继续条件**：单步不超过 0.18 秒（约 2.5 天以内）才开正式训练；否则带着 profiler 结果回来再定。

## 质量判定（预注册）

arch2 与 arch1 用同样的数据、同样的步数，在 development 上比较：

1. 主指标：公开拼音集自身重打分 Top-1（λ = 1.6），句子簇 sign-flip 配对检验。
2. arch2 取代 arch1 成为 800M 的条件（两条都要满足）：
   - 主指标不显著低于 arch1；
   - Standard 全拼重排的 Top-1 不显著低于 arch1。
3. 联想（轨道 A–D）和各测点 BPC 是描述性的。
4. 第四轮蒸馏用两者中主指标更高的一个当老师。

## 时间线与版本

- arch2 在 arch1 训完、评测完之后再开工。先做第 0 步，再写代码。
- 发布名 `vimeml-zh-v2-800m` 指 arch1。arch2 赶得上 v2 定版并通过判定，就替换它；赶不上就进入下一版。

## 不做的事

- 文档级长上下文、更换词表、重建窗口；
- MoE、FSDP（模型加优化器状态单卡放得下）；
- 改学习率、步数或 loss 归一化。

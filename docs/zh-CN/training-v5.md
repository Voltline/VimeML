# V5 规模扩展预训练

V5 把 V4.3 的训练方案原样放大到 d512/L8，检验 15M 模型的瓶颈是否在容量。数据、seed、目标函数、优化器和训练预算都与 V4.3 相同，只改变模型规模。状态：controlled-10ep 与 30 轮均已训练并完成本地评估。结论是：更大的模型显著降低了 BPC，但没有提升 IME Top-1；V5 不进行 Core ML 转换和设备测量；部署仍为 V2.1，V4.2 保持可选变体。

## 动机：V4.3 已饱和

V4.3 在 V4.2 数据池上加入九个 FineWeb2-Edu 分片（跨池去重，每轮网页窗口约翻倍）。在同一份原验证文本上：

| 运行 | 监督 token | LM BPC |
| --- | ---: | ---: |
| V4.2，20 轮 | 约 12B | 3.045152 |
| V4.3 controlled，10 轮 | 约 12B | 3.048984 |
| V4.3，30 轮 | 约 36B | 3.043831 |

同样约 12B token 下，两倍的新数据没有带来 BPC 改善；token 增加到三倍，BPC 也只降低 0.0013。三次运行都收敛到约 3.04，与训练长度和数据量无关。本地四组 FP32 Top-1（Standard /728、Legacy /500、AJIMEE /200、历史 dev /137）：V4.2 第 20 轮为 523/370/139/123，V4.3 第 30 轮为 519/367/143/123，V4.3 第 27 轮为 521/372/138/124，相对 V4.2 的差异都不显著。15M 模型的容量看起来已经用尽，V4.3 不再进行 Core ML 转换和设备测量。

V4.3 的源码与配置已导入仓库（`joint_v43.py`、`v43_data.py`、`train-v43.toml`、`train-v43-10ep.toml`），与运行记录的 `code_sha256` 逐字节一致。本地评估入口为 [`evaluate_v43.py`](../../scripts/benchmarks/evaluate_v43.py)，结果在 `outputs/evaluation-v43-20261020/`。

## 架构

| 项目 | V4.2/V4.3 | V5 |
| --- | --- | --- |
| d_model / 层数 / 头数 | 384 / 7 / 6 | 512 / 8 / 8 |
| SwiGLU 宽度 | 960 | 1280 |
| 参数 | 15,070,848 | 28,385,792 |
| 每层参数 | 1,696,512 | 3,015,680 |
| KV cache 形状 | (7,1,6,128,64) | (8,1,8,128,64) |

头宽保持 64；FFN 宽度保持 d 的 2.5 倍。其余与 V4 相同：RMSNorm、SwiGLU、无 bias、tied head、learned position、context 128。tokenizer 沿用 V4 的 8K Unigram（SHA256 `296a2bdf…81b5`）。tokenizer 只决定文本如何切分，与模型宽度无关，而且 V4.3 数据池已用它编码，所以不需要重新训练或重新测试。

V5 是独立的架构身份（`tiny_gpt_v5` / `vimeml_tiny_gpt_v5`）。V4 的固定配置与参数校验保持不变，`TinyGPTV4` 加载 V5 checkpoint 会报错，反之亦然。

## 训练设置

两次运行与对应的 V4.3 配置只差 stage、architecture、模型尺寸和输出路径：

| 配置 | 对照 | 轮数 |
| --- | --- | --- |
| [`train-v5.toml`](../../configs/train-v5.toml)（controlled-10ep） | `train-v43-10ep.toml` | 10 轮，约 12B 监督 token |
| [`train-v5-30ep.toml`](../../configs/train-v5-30ep.toml) | `train-v43.toml` | 30 轮，约 36B 监督 token |

| 项目 | 设置 |
| --- | --- |
| 数据 | 冻结的 V4.3 混合 `corpus-v43-mixed-c128`（manifest `81d7e610…`），按轮数使用前 10 个或全部 30 个映射 |
| Seed | 1219827974 |
| 目标 | 普通无标记 next-token loss，按每次更新的监督 token 数归一化，5% 聊天 |
| 优化 | fused AdamW，lr 6e-4 → 6e-5 cosine，1,000 warmup，wd 0.1，clip 1.0，batch 512 |
| 精度 | BF16 AMP、编译主干；每轮完整 FP32 验证（旧 LM、扩充网页、聊天） |

由于每轮数据映射、裁剪和采样都与 V4.3 一致，V5 与同轮数 V4.3 的差异只能来自模型规模。权重初始化随形状不同而不同，这一点无法避免。

## 集群操作

```bash
VIMEML_PYTHON=/path/to/venv/bin/python python scripts/training/train_v5.py --dry-run   # 校验配置、代码、数据身份
VIMEML_PYTHON=/path/to/venv/bin/python bash scripts/training/cluster_v5.sh             # 存在 last.pt 时自动续训
```

需要的集群数据与 V4.3 相同：`corpus-v4-8k`、`corpus-v4-c128`、`corpus-v43-exp8k`、`corpus-v41-chat-8k` 及其窗口索引、排除掩码、`corpus-v43-mixed-c128` 的映射文件。

实际开销（单张 L20C）：controlled-10ep 更新时间 3.83 小时，30 轮 11.83 小时；峰值分配显存 12.7 GiB。

## 结果

运行产物位于 HF 私有数据集 `Voltline/vimeml-v5-training-output`（revision `01e93a6…`）：根目录是 30 轮运行，`controlled-10ep/` 是 10 轮运行。两次运行的 `code_sha256` 与仓库代码逐字节一致（90 个文件），记录中的配置与上面两个 TOML 完全相等。下载校验记录在 `outputs/training-v5-20261021/download-receipt.json`。

### 验证 BPC

两次运行的完整 LM BPC 都在最后一轮达到最佳（`best-lm.pt` 即最后一轮）：

| 运行 | LM BPC | 扩充网页 BPC | 聊天 BPC |
| --- | ---: | ---: | ---: |
| V4.3 controlled，10 轮 | 3.048984 | 3.055103 | 3.110230 |
| **V5 controlled，10 轮** | **2.948747** | **2.952379** | **3.084419** |
| V4.3，30 轮 | 3.043831 | 3.049611 | 3.128712 |
| **V5，30 轮** | **2.942180** | **2.945641** | **3.108036** |

相同数据和预算下，V5 的 LM BPC 低约 0.10，是项目迄今最好的结果；V5 训练 10 轮就已优于 V4.3 训练 30 轮。在 30 轮运行中，V5 与 V4.3 的差距从第 1 轮的 0.077 逐渐扩大到第 30 轮的 0.102。与 V4.3 一样，延长到 30 轮只带来很小的额外收益（−0.007）。

### IME Top-1（本地 FP32）

评估入口为 [`evaluate_v5.py`](../../scripts/benchmarks/evaluate_v5.py)，语义与 V4.2/V4.3 相同：完整词表后缀 logP 求和、上下文与候选联合分词、FP32、关闭 TF32、稳定排序。fixed reference 与 blind 集未读取。结果在 `outputs/evaluation-v5-20261021/`。

| 模型 | Standard /728 | Legacy /500 | AJIMEE /200 | 历史 dev /137 |
| --- | ---: | ---: | ---: | ---: |
| V2.1 | 505 | 374 | 144 | 122 |
| V4.2 第 20 轮 | 523 | 370 | 139 | 123 |
| V4.3 controlled 第 10 轮 | 514 | 378 | 142 | 125 |
| V4.3 第 30 轮 | 519 | 367 | 143 | 123 |
| **V5 controlled 第 10 轮** | **504** | **372** | **145** | **123** |
| **V5 第 30 轮（主候选）** | **514** | **365** | **145** | **124** |
| V5 第 29 轮（仅描述） | 522 | 373 | 145 | 122 |

两组只改规模的对照中，没有一个 track 显著，方向也不一致。V5-10ep 对 V4.2 在 Standard 上为 −19（+29/−48，p=0.040），是全部对比中唯一名义显著的结果；考虑到同时做了十几组比较，不能把它当作稳健的退化。

### 选点说明

按预先确定的规则，主候选是 BPC 最佳的第 30 轮。集群端推荐过第 29 轮，理由是它在 dev 上 Standard 522、AJIMEE 145，"最平衡"。这个选择不成立：

- 第 29 轮的 LM BPC（2.9523）比第 27 轮（2.9508）、第 28 轮（2.9454）和第 30 轮都差，选它只能依据 dev IME 分数，属于在 dev 集上的选择偏差。
- 第 29 轮与第 30 轮之间，Standard 上有 62 题翻转，净差 +8（+35/−27，p=0.37）。相邻两轮之间的差异本身就是这个量级，可见它是噪声。

另外，`controlled-10ep/README.md` 中的 IME 一行（"best Standard 522 (epoch 29)"）是从 30 轮的 README 复制过来的。10 轮运行实测 Standard 为 504。

## 结论

1. **规模有效降低了困惑度，但没有转化为 IME 准确率。** 增加数据（V4.3）和加大模型（V5）两条路线都改善了 BPC，可 Top-1 始终停在 Standard 504–523、AJIMEE 138–145 之间，变化都在配对噪声范围内。在当前"固定 AzooKey 候选池 + 后缀 logP 求和"的重排方式下，LM 质量已不是瓶颈。
2. **V5 不进入部署。** 它的参数是 V4.2 的 1.9 倍，INT8 包约 32 MB，按 V4.2 实测线性外推，iPhone 无状态重排 p95 约 230 ms，接近 250 ms 的软预算，却没有换来准确率。因此不把 `vimeml.deployment.v4*` 推广到 V5，也不做 Core ML 转换和真机测量。
3. **不动用 blind 集。** V5 没有替换 V2.1 或 V4.2 的依据，因此不预注册，也不评分从未用过的 1,000 题 blind 集。
4. **后续方向转向打分本身，而不是继续扩大预训练。** V4.2 相对 V2.1 的 Top-1 翻转中有 61% 是书写形式差异，单纯降低 BPC 解决不了这一类。值得尝试的方向包括：长度与书写形式的归一化、利用 AzooKey 原排名作先验，以及在 IME 数据上做后训练。V5 checkpoint 保留，可作为这些实验中更强的 LM 底座。[错误分解](reports/analysis-20261021/ime-errors.md)显示，Standard 上剩余错误主要来自候选池缺失和书写形式差异，明确的语义错误只有十几个。

## 结论边界

只改规模的对照能回答"更大的模型在相同数据和预算下是否更好"：在 LM 上是，在 IME 重排上否。它不能回答其他打分方式、后训练或其他数据配比下规模是否有用。所有 IME 数字都来自非 blind 的开发集与回归集，只用于描述和否定性结论，不作为最终发布裁决。

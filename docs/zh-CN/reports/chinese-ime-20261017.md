# 中文输入法本地调研：2026-10-17

已在本机实际运行 **4M、25M、Rime＋Octagram 和 PinyinGPT-Concat**。4M 值得作为中文版后续实验的轻量基线，25M 适合作为桌面精度对照；现阶段更应关注完整候选召回、上下文策略和改错风险。此次只增加独立调研脚本和报告，没有改动现有日文训练链路或客户端。

[英文完整实验记录](../../reports/chinese-ime-20261017.md)是主要技术记录，包含完整参数、修订号、摘要、方法和限制。这里的分数均为小型参考集或诊断集上的精确匹配数，不是产品准确率。

## 整句结果：候选生成决定重排有没有用

输入包含作者原有的 60 条手写整句参考样例，另有本次预先编写并冻结的 32 条成对上下文探针、13 条鲁棒性探针，共 105 条。两个重排模型在打分前选定，未训练、未扫阈值，也没有用这些标签做模型选择。

Rime 使用独立词库目录，关闭用户学习和补全，保留引擎顺序的前 9 个候选，不把答案塞进候选池。逐个在新会话中选择候选，只有确实上屏完整文本的候选才标记为回答整个输入，避免把前缀混入整句排序。

60 条整句的结果：

| 候选生成配置 | 引擎原首选 | 加 4M | 加 25M | 正确答案在完整候选池中 |
|---|---:|---:|---:|---:|
| Rime 默认单整句 | 41 | 41 | 41 | 41 |
| Rime＋Octagram 默认单整句 | 45 | 45 | 45 | 45 |
| Rime 多整句 | 41 | 44 | 46 | 46 |
| Rime＋Octagram 多整句 | 45 | **49** | **52** | **54** |

默认配置里，每条整句实际上只有一个完整候选，其余大多是前缀，因此模型没有可替换的完整答案。多整句实验另设 `translator/max_sentences: 9` 和 `sentence_cutoff_threshold: 1.0`，保留默认池作对照，没有覆盖它。

在 Octagram 多整句池上，4M **救回 7 条、改错 3 条**；25M **救回 8 条、改错 1 条**。25M 的 52 条仍低于本候选池 54 条的可达上限。这也不是复现模型卡的 52/56：本次使用的引擎、候选列表和分母均不同。

上游已指出其中 12 条以 `ta` 开头的样例存在“他／她”等不可判歧义。按其说明排除这 12 条，剩余 48 条在 Octagram 多整句池上的结果为 **33 → 37 → 40**，候选可达 **42**。这只是敏感性检查，不能把剩余集合称为新盲测。

两个模型在 60 条上的正确集合只相差 3 条，精确双侧 McNemar p=0.25，不足以证明稳定的精度名次。救回数与改错数比单一总分更值得保留。

## 上下文、词典门控和错误输入

32 条上下文探针对同音词提供不同左文，31 条答案出现在 Rime 池中。引擎命中本次预设标签 15 条；关闭门控直接按模型分数选择时，4M 有上下文为 **18/32**、无上下文为 **11/32**，25M 分别为 **20/32**、**10/32**。相对引擎，4M 救回 5 条、改错 2 条，25M 救回 6 条、改错 1 条。

这些标签是本次编写的预期，不是母语人工审核 gold，部分表达也可能允许不同写法，例如某条中的“终止／中止”。这些数值只能观察行为。

Rime 公共 C API 没有暴露原项目需要的精确候选来源，因此此处使用“原词典中存在完全一致的文本／拼音对”作为**词典来源代理**，并同时检查完整覆盖。它不能直接充当产品中的候选来源标签，特别是存在纠错或拼写变体时。按这个代理启用官方门控，32 条探针全部保留词典首选，仍为 15/32。直接照搬“词典命中一律不动”会压住上下文消歧收益，而一律覆盖词典又会引入回退；中文版需要自己的策略评测。

13 条鲁棒性探针包含简拼、混合简拼、错序／缺字母、`xian` 与 `xi'an`、数字混输和九键字符串。Octagram 多整句池原首选命中 4 条、答案可达 7 条；门控 4M 为 5 条（救回 2、改错 1），25M 为 6 条（救回 2、改错 0）。所用 Rime 方案不支持九键。这不是通用纠错能力测试。

## 体积、CPU 延迟和加载内存

本机为 Windows 11、Intel Core Ultra 7 255HX，暴露 20 个逻辑 CPU；官方 Rust release 构建保持 INT8 矩阵。没有测 iPhone、Android 或 Core ML。以下均为十进制 MB。

| 测量 | 4M | 25M |
|---|---:|---:|
| 权重文件 | 4.486 MB | 25.480 MB |
| 加载完成的整个进程工作集 | 约 10.0 MB | 约 31.7 MB |
| 启动期间峰值工作集 | 约 14.9 MB | 约 57.1 MB |
| 真实多整句池，实际触发重排，p50 / p95 | 11.45 / 27.07 ms | 70.64 / 141.96 ms |
| 9 候选 × 8 字，整池重算，p50 / p95 | 30.96 / 34.28 ms | 169.57 / 177.03 ms |
| 9 候选 × 15 字，整池重算，p50 / p95 | 58.29 / 75.06 ms | 318.44 / 343.81 ms |
| 合成逐字延长轨迹，第 8 步缓存续算，p50 / p95 | 4.24 / 6.25 ms | 33.27 / 35.13 ms |
| 同一轨迹第 15 步，p50 / p95 | 4.51 / 5.53 ms | 35.12 / 37.46 ms |

真实池延迟只统计实际触发模型且有至少两个完整候选的请求，未把跳过请求混入平均数。官方形状扫描每格 40 次；长句格可能重复候选，原程序有明确提示。后面的累计打字扫描与其他准备工作有重叠，这里没有引用其累计数值。

另做的缓存轨迹有 9 个首字不同的候选，每一步延长一个汉字，重复 30 次，每次从新缓存开始，不反复访问已经算完的候选列表。它测量的是合成增量成本，不是真实拼音按键、分词变化或整套输入法延迟。缓存与重新计算的分数误差小于 1e-4。官方脚本的“完全相同候选列表再次调用”微秒结果没有被当作打字延迟。

工作集在加载后暂停进程测得，已释放多余的文件字节缓冲；它包含进程开销，不包含实际键盘扩展的词典、引擎和预热缓存。Windows 功耗、调度和温度未严格控制。文件很小不等于每次重排都能落在一帧之内。

## PinyinGPT 实跑结果

README 中原 `visualjoyce` 模型地址返回访问错误，改为获取公开可访问的 [`aihijo` 检查点](https://huggingface.co/aihijo/transformers4ime-pinyingpt-concat)，固定修订并核对 SHA256。该模型有 **102,408,960** 个独立参数，PyTorch 文件为 **488,536,999 字节**。

旧代码依赖 Transformers ~4.15／PyTorch ~1.10，本次在隔离适配器中使用 Transformers 4.57.6、上游 segmented prompt、aligned 位置、每音节汉字约束、beam=16 和 10 个返回结果。发布配置漏记了权重里已经存在的 443 个拼音 token，加载前把词表改为 21,571；没有缺失学习权重，只忽略旧版注意力掩码缓冲。一次缓存与完整前向检查的最大 logits 误差为 4.77e-6。

本次**根据目标文本生成音节和音节边界**，简拼取每个音节首字母。这沿用上游评测输入构造方式，但不等于用户原始连续按键测试，也没有实现纠错或九键。

| 已分音节的任务 | Top-1 | Top-10 |
|---|---:|---:|
| 60 条参考句，全拼 | 44/60 | 46/60 |
| 60 条参考句，逐音节首字母简拼 | 14/60 | 28/60 |
| 仅保留与原始键串读音一致的全拼 | 38/53 | 39/53 |
| 对应 53 条的简拼 | 13/53 | 26/53 |
| 32 条上下文探针，全拼 | 29/32 | 32/32 |
| 32 条上下文探针，简拼 | 28/32 | 31/32 |

有 7 条原始 TSV 键串与自动生成读音不同，所以另外列出一致的 53 条；这一子集仍然具有答案提供的音节边界。PinyinGPT 的候选空间也与 Rime 不同，不能把这张表与重排表当成公平排行榜，更不能宣称复现了论文成绩。

使用 RTX 5060 Laptop GPU、FP32，峰值已分配张量内存约 488.2 MB。整句全拼生成 p50/p95 为 97.7/165.1 ms，简拼为 98.7/180.4 ms，双字上下文探针约 35–39 ms。这轮 GPU 计时与 Rime 候选采集有重叠，只作为初步运行记录，不与 CPU 重排做严格速度比较。

## 验证与复跑

上游 Rust 测试 **59 项通过、10 项显式忽略**；两个官方 `verify` 均通过。每个模型的 **3,016 个候选分数**与上游 PyTorch 前向对照，4M 最大误差 5.96e-5、25M 为 1.20e-4 nats/字，**最佳候选分歧均为 0**。这支持此次适配与记录的正确性，不是逐位一致证明。

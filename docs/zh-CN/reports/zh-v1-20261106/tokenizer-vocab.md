# vimeml-tiny-zh-v1 tokenizer：词表大小与字符覆盖率（2026-11-06）

这是一次探索性对比，只训练了 tokenizer，没有训练任何语言模型，也没有算 BPC 或 IME 准确率。目的是在开训前弄清楚：词表从 8K 加到 32K，压缩率能提升多少；在固定参数预算下，要为此付出多少层；字符覆盖率对罕见字有什么影响。

结论先写在前面：

- **20M 模型只实验 8K 和 12K，覆盖率都用 0.9995。** 12K 是最均衡的选择，8K 作为对照。两者谁更好，要在同等算力下比较 BPC 和 IME 结果才能定。
- **200M 模型再考虑 16K、24K、32K**，每种词表各开一组实验。
- **覆盖率 0.9999 不采用。** 罕见字的字节回退确实降下来了，但多字词的名额几乎被单字占光，12K 的压缩率退回到 8K 的水平。
- **正式训练 tokenizer 时，要把 `\n` 设为 user_defined_symbol。** 本次统计到的字节 token 里，九成是换行符（见下文）。

## 设置

入口：[probe_zh_v13_vocab.py](../../../../scripts/tokenizer/probe_zh_v13_vocab.py)（训练和统计）、[probe_zh_v13_bytes.py](../../../../scripts/tokenizer/probe_zh_v13_bytes.py)（去掉换行后的字节回退）。产物在 `outputs/tokenizer/zh-v13-vocab-probe/`，不进 Git。每个变体一个目录，里面有 `tokenizer.model`、`tokenizer.vocab` 和 `stats.json`。

```powershell
.venv/Scripts/python.exe -I -X utf8 scripts/tokenizer/probe_zh_v13_vocab.py . outputs/tokenizer/zh-v13-vocab-probe
.venv/Scripts/python.exe -I -X utf8 scripts/tokenizer/probe_zh_v13_bytes.py . outputs/tokenizer/zh-v13-vocab-probe
```

实际运行时，变体列表里还有 8K / 0.9999，训练到这一项时报错退出，因为 0.9999 覆盖率需要 10,417 个必需字符，超过了 8,192 的词表大小。12K / 0.9999 是随后用同一个训练样本、同样的设置补训的。仓库里的脚本已经去掉了 8K / 0.9999。

**训练样本**：来自 [zh-v13-export-r1](../../data-zh-v1.md) 的 train。

- 网页：38 个 web 文件，每个文件随机取 2 个 row group，按换行切成段落（单段不超过 16KB UTF-8），每个文件抽 39,474 段，共 1,500,000 段。
- 聊天：LCCC train 随机抽 80,000 条，约占 5%。
- 两部分打乱后写成一个文件 `train-sample.txt`。所有变体读同一个文件，不再重新抽样。
- 合计 97,396,787 字，其中汉字 80,500,741。种子 20261106，文件 SHA256 `2ed06667da76300b1ca5b144c1b5bb448aed8ae9fe8ac707bcf0990fde4484de`。
- 此时审核队列那部分还没导出，所以样本里只有自动保留的网页和 LCCC。

**SentencePiece 0.2.1 参数**：Unigram，`normalization_rule_name=identity`，`byte_fallback=true`，`add_dummy_prefix=false`，`remove_extra_whitespaces=false`，`split_digits=false`，`hard_vocab_limit=true`，`seed_sentencepiece_size=1,000,000`。PAD/UNK/BOS/EOS = 0/1/2/3。这次没有加 `<CTX>/<READ>/<OUT>` 这类任务标记，所以和正式 tokenizer 相比差 3 个词表名额，不影响比较。

**评估数据**：

| 集合 | 规模 | 用途 |
| --- | --- | --- |
| export-r1 validation，网页 | 14,681 篇，19,184,275 字（汉字 15,622,687），段间换行 281,051 个 | 压缩率、字节回退、上下文容量 |

基准只读取 `split == development` 的条目，blind 条目在读入时就丢弃，没有参与任何计算。validation 不参与 tokenizer 训练。

## 结果

除注明外，数字都来自网页 validation。“字节回退”是字节 token 占全部 token 的比例，已去掉换行符。

| 词表 / 覆盖率 | 每汉字 token（网页） | 每汉字 token（聊天） | 126 token 覆盖字数 | 字节回退 | 单字 / 多字词 / 其他 | 多字词平均长度 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 8K / 0.9995 | 0.989 | 0.949 | 156 | 0.19% | 5623 / 1468 / 841 | 2.06 |
| 12K / 0.9995 | 0.878 | 0.855 | 176 | 0.22% | 5623 / 5108 / 1297 | 2.19 |
| 16K / 0.9995 | 0.834 | 0.809 | 186 | 0.23% | 5623 / 8805 / 1696 | 2.28 |
| 24K / 0.9995 | 0.787 | 0.764 | 197 | 0.24% | 5623 / 16168 / 2525 | 2.46 |
| 32K / 0.9995 | 0.758 | 0.738 | 204 | 0.25% | 5623 / 23570 / 3315 | 2.61 |
| 12K / 0.9999 | 0.977 | 0.935 | 159 | 0.05% | 8341 / 1678 / 2009 | 2.06 |

“其他”是含非汉字的词片，包括标点、字母、数字和混合词片；字节 token 和特殊 token 不计入这三列。“126 token 覆盖字数”按 126 × 字数 / token 数估算（上下文 128 去掉 BOS/EOS），不是实测的打包窗口。

基准 development 上的统计：

| 词表 / 覆盖率 | 每个候选 token | 每个参考答案 token | 候选含字节回退 | 前文切分不变 |
| --- | ---: | ---: | ---: | ---: |
| 8K / 0.9995 | 4.47 | 4.20 | 0.38% | 98.0% |
| 12K / 0.9995 | 4.06 | 3.67 | 0.38% | 96.3% |
| 16K / 0.9995 | 3.89 | 3.43 | 0.38% | 95.3% |
| 24K / 0.9995 | 3.73 | 3.24 | 0.38% | 93.8% |
| 32K / 0.9995 | 3.67 | 3.16 | 0.38% | 93.0% |
| 12K / 0.9999 | 4.42 | 4.12 | 0.03% | 98.0% |

“前文切分不变”的意思是：把前文和候选连起来编码后，开头那一段 token 恰好等于前文单独编码的结果。不相等时，候选的首个词片和前文末尾合并了，按“前文 token + 候选 token”打分就要另外处理边界。

## 20M 预算下的参数分配

按 vimeml-tiny-zh-v1 计划的模型族计算：d384、SwiGLU d_ff 960、learned position 128、embedding 与输出层共享，总参数约 20M。每层参数 4·d² + 3·d·d_ff + 2·d = 1,696,512。层数取最接近预算的整数。

| 词表 | 层数 | embedding | 主干 | 总参数 | 输出层占每 token 计算 | 每汉字计算（乘加） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 8K | 10 | 3.15M | 16.97M | 20.16M | 15% | 20.9M |
| 12K | 9 | 4.72M | 15.27M | 20.04M | 23% | 18.3M |
| 16K | 8 | 6.29M | 13.57M | 19.91M | 31% | 17.2M |
| 24K | 6 | 9.44M | 10.18M | 19.67M | 47% | 15.9M |
| 32K | 4 | 12.58M | 6.79M | 19.42M | 64% | 15.0M |

每 token 计算 = 主干权重 + 注意力（每层 2·128·d）+ 输出层（V·d），再乘每汉字 token 数得到每汉字计算。词表变大以后，每个汉字的计算略有下降，但省下的主要是主干的计算，模型容量也跟着变小。12K / 0.9999 和 12K / 0.9995 的参数相同，但因为压缩率更低，每汉字计算是 20.4M。

## 观察

**1. 压缩率的收益递减得很快。** 8K 到 12K，每汉字 token 少 11%；12K 到 16K 少 5%；16K 到 32K 一共只少 9%。在 20M 预算下，16K 比 12K 少一层，而压缩率只多 5%；到 24K、32K，主干只剩 6 层和 4 层，输出层要占一半以上的计算。

**2. 覆盖率决定单字，词表大小只决定多字词。** 覆盖率 0.9995 时，不管词表多大，单字都是同样的 5,623 个；增加的名额全部给了多字词，多字词也越来越长（平均 2.06 字到 2.61 字）。所以罕见字的回退也不随词表变化：validation 里出现的 8,132 个不同汉字中，有 2,532 个没有单字词片，它们占汉字出现次数的 0.045%，例如 抟、绗、蛉、佧、訇、钿。

**3. 0.9999 覆盖率用 12K 的参数换来了 8K 的压缩率。** 0.9999 时单字增加到 8,341 个，加上字节 token 等其他固定项，多字词只剩 1,678 个名额。罕见字回退降到 0.009%（validation 中没有单字词片的汉字降到 890 个），候选含字节回退从 0.38% 降到 0.03%；但每汉字 token 从 0.878 回到 0.977，几乎和 8K 一样。为了 0.38% 的候选回退，不值得放弃 11% 的压缩率。

**4. 词表越大，前文和候选之间越容易合并。** 前文切分不变的比例从 8K 的 98.0% 降到 32K 的 93.0%。这对 IME 打分有影响：如果直接用前文单独编码的 token 后接候选打分，切分会和训练时见到的不一样。

**5. 字节 token 九成是换行符。** 训练样本按段落切开，样本里没有换行，所以词表里也没有换行，validation 里每个段间换行都退化成一个 `<0x0A>` 字节 token。以 8K 为例，含换行时字节 token 占 2.01%，其中 91% 是换行；去掉换行后只有 0.19%。之前 12K 试探里看到的 2.25% 也是这个原因。换行无论是字节 token 还是独立词片都只占一个 token，所以 token 数、压缩率和上下文容量不受影响。但正式 tokenizer 应当把 `\n` 设为 user_defined_symbol，保证它有固定的 id，也不和字节 token 混在一起。

**6. 训练时间不是问题。** 每个变体在本机训练约 200–240 秒（16 线程）。

## 后续实验安排（2026-11-06 决定）

**20M 模型**：只比较 8K / 0.9995 和 12K / 0.9995。12K 是最均衡的：上下文多覆盖 20 个字，候选短 9%，只少一层。8K 多一层主干，输出层的计算更少；日文 V4 选了 8K，理由正是这个。中文要以同等算力下的 BPC 和 Standard 中文 development 结果为准，单种子的差别要放在种子噪声范围里看。

**200M 模型**：16K、24K、32K 各开一组实验。在这个规模下 embedding 的占比小得多。例如 d1024 时，32K 词表的 embedding 是 33.6M，约占 200M 的 17%；而在 20M 预算下，32K 的 embedding 要占总参数的 65%。所以大词表的代价在 200M 上可以接受，具体的 d 和层数等 200M 方案定下来再算。

**正式 tokenizer 和这次的区别**：

- 训练样本要包含审核队列导出的部分，等 export-r1 完成后再训。
- 加上 `\n` 和任务标记（`<CTX>/<READ>/<OUT>` 或中文模型的对应标记）作为 user_defined_symbols。
- 保留本次的其余设置：Unigram、identity、byte_fallback、0.9995 覆盖率、hard vocab limit。
- 这次的 tokenizer 只是探索产物，不直接用来训练模型。

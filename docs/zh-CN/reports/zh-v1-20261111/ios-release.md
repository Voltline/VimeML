# vimeml-tiny-zh-v1 Mac 交接结果核对与 iOS 发布（2026-11-11）

Mac 端完成了 Core ML 转换、INT8 量化、量化方案调查和 Mac 实测，过程和全部数字见 [Mac 报告](../../../reports/mac-20261111/zh-v1-coreml.md)（英文）。本文做三件事：在 Windows 上独立核对交接包，分析结果，记录发布到 Hugging Face 的内容。这一版将部署到 iOS。

交接包 `vimeml-zh-v1-mac-results-20261111.zip`，SHA256 `0a97da02650bbbd9a4e32f4ec8f389047c4026b29666470649f9cc7af191b3bf`，171 个文件。只用到 development；blind 没有再读。

## 结论

- **iOS 用 INT8 block32**（只量化权重，FP32 计算，CPU_ONLY，iOS 18 起），有无状态和分块 KV 两个包。和 FP32 相比，development 全拼 Top-1 +2/−1，简拼 +0/−2，Top-3 两条轨道都没有变化，差别在噪声范围内。
- **交接包核对通过**：文件大小、bundle 哈希、权重与训练 checkpoint 逐张量一致，Mac 的逐题结果和 Windows 的逐题排名一致（见下一节）。
- **iPhone 实测已补（见“iPhone 与模拟器实测”）**：iPhone 16 Pro Max 测试宿主上无状态 INT8 `predict` T=128 p50 为 6.82 ms，V4.2 为 4.90 ms，是 1.39 倍，与 Mac 上的比例一致（此前按比例估计约 6.5 ms）。加载并预测 50 次后的内存增量是 14.1 MiB，比 V4.2 多 2.8 MiB。
- **键盘扩展集成实测已补（见“键盘扩展集成实测”）**：模型在扩展里给 Rime 的前 8 个候选重排。开模型后，从按键到候选可点的时间平均 26.1 ms，p95 45.0 ms；关模型时是 20.3 ms 和 26.1 ms。222 次打分有 221 次在 60 ms 窗口内完成，扩展内存峰值 29.9 MiB。中文联想还没做，所以没测。
- **训练数据许可**：LCCC 的仓库和 Hugging Face 数据卡标的是 MIT，但仓库 README 的免责声明写明数据集和预训练对话模型“仅限科研用途”。项目负责人决定直接公开发布，模型卡和 NOTICE 如实写出两处条款。详见“许可”一节。

## 结果分析

### 量化对排序的影响

参照为 Core ML FP32（与 Mac PyTorch、Windows CUDA 的 Top-1 都是 1,363 / 337）。

| 包 | 体积 | 全拼 Top-1（1,456） | 简拼 Top-1（990） | 对 FP32 多对 / 多错 | 结论 |
| --- | ---: | ---: | ---: | --- | --- |
| FP32 | 80.4 MB | 1,363 | 337 | — | 基准 |
| **INT8 b32（部署）** | **22.8 MB** | 1,364 | 335 | 全拼 +2/−1，简拼 +0/−2 | 无显著差异，Top-3 不变 |
| INT8 b32 + FP16 词嵌入 | 26.9 MB | 1,365 | 337 | +2/−0，+0/−0 | 无显著差异，大 18% |
| 调色板 6 bit | 15.7 MB | 1,364 | 339 | +7/−6，+4/−2 | Top-1 持平，但排序变动多 |
| INT4 b32 | 12.8 MB | 1,349 | 332 | +10/−24，+8/−13 | 全拼显著变差（p = 0.024） |
| 调色板 4 bit | 10.4 MB | 1,320 | 316 | +16/−59，+17/−38 | 显著变差（p = 6e-7） |

- INT8 的严格 logits 门槛照例不通过（最大误差 0.392，V4.2 是 0.477），这是有损量化的预期漂移，不是数值等价。分块 KV INT8 和无状态 INT8 在 21 项检查里最大差 4.2e-5，排序完全相同，所以两个 INT8 包可以互换。
- 6 bit 调色板的 Top-1 和 FP32 持平，但改变了全拼 1,424 题、简拼 983 题的候选顺序，第一候选变化 15 + 62 题，比 INT8 的 4 + 17 题多得多。只看 Top-1 会低估它的误差。用在 iOS 上还需要单独评估。
- 这次调查按计划只记录数字，不换方案。如果以后在意 18% 的体积，可以考虑 FP16 词嵌入；如果在意更小的体积，6 bit 调色板值得先在联想基准上看看。

### Mac 性能（与 V4.2 同机、交错测量）

| 指标 | zh-v1 INT8 | V4.2 INT8 | 比值 |
| --- | ---: | ---: | ---: |
| 包体积 | 22.8 MB | 17.2 MB | 1.33× |
| 无状态 `predict` p50，T=1 / T=128 | 1.65 / 8.49 ms | 1.29 / 6.43 ms | 1.28× / 1.32× |
| 分块 KV 预填 119 token / 单步解码 p50 | 9.33 / 2.71 ms | 7.18 / 2.05 ms | 1.30× / 1.32× |
| 模型自身的峰值内存增量 | 18.4 MiB | 13.4 MiB | 1.37× |

比值和词表（12,288 对 8,192）、层数（9 对 7）的增加相符。INT8 只缩小体积，不降低 CPU 延迟，因为计算仍是 FP32。

### iPhone 与模拟器实测（2026-11-11）

Vime 维护者用 `benchmark_lm_variants.py --variants zhV1,v42` 在 Vime 测试宿主里测量：iPhone 16 Pro Max（iOS 27.3）和 iOS 模拟器（iOS 27.2）各 4 轮，两个模型每轮交替，每个 run 是单独的测试进程。16 个 run 全部通过，热状态始终 nominal，没有开低电量模式。下表是 iPhone 4 轮的中位数；`predict` 为无状态 INT8 包、CPU_ONLY，每个长度 10 次取 p50。

| 指标 | zh-v1 INT8 | V4.2 INT8 | 比值 |
| --- | ---: | ---: | ---: |
| `predict` p50，T=1 | 1.70 ms | 1.25 ms | 1.35× |
| `predict` p50，T=8 / 16 / 32 | 2.25 / 2.37 / 3.31 ms | 1.68 / 1.78 / 2.45 ms | 1.34× / 1.33× / 1.35× |
| `predict` p50，T=64 / 128 | 4.56 / 6.82 ms | 3.30 / 4.90 ms | 1.38× / 1.39× |
| `predict` p95，T=128 | 6.97 ms | 5.04 ms | 1.38× |
| 加载 / 重新加载 | 195 / 7.4 ms | 155 / 5.9 ms | 1.26× / 1.26× |
| 首次 `predict`（不含第 0 轮冷启动） | 6.2 ms | 4.5 ms | 1.39× |
| 内存增量：加载并预测 50 次后 | 14.1 MiB | 11.3 MiB | 1.25× |
| 内存增量：测试过程峰值 | 20.0 MiB | 18.8 MiB | — |

- 延迟比例和 Mac 上的 1.28–1.32 倍基本一致，略高一点，原因与 Mac 相同：词表 12,288 对 8,192，层数 9 对 7。T=128 的 p95 只比 p50 高 2%，4 轮之间的波动也很小。
- 第 0 轮 zh-v1 的加载 244 ms、首次 `predict` 13.9 ms 是冷启动；其后 3 轮稳定在 174–201 ms 和 6.2 ms。V4.2 的 4 轮加载在 144–167 ms 之间，首次 `predict` 都在 4.4–4.6 ms，没有明显的首轮差异。
- 内存峰值不能直接比：V4.2 的 run 还包含日文候选重排和联想（重排后内存 40.9 MiB），zh-v1 的 run 跳过了这些日文流程。只看模型本身，加载并预测 50 次后 zh-v1 多占 2.8 MiB。Mac 报告里多 5.0 MiB 的是模型峰值增量，两者口径不同。
- 模拟器的数字只说明功能可用，不代表真机性能：zh-v1 的 T=128 p50 是 69.4 ms，V4.2 是 44.7 ms，都比真机慢 9 倍以上，而且轮间波动大。此前的模拟器功能检查（资源身份、logits 形状、原生 SentencePiece 分词、联合打分）4/4 通过。

### 键盘扩展集成实测（2026-11-11）

结果来自 Vime 维护者的第二个交接包 `zh-v1-vime-integration-20261111.zip`。测试设备是 iPhone 16 Pro Max（iOS 27.3），用优化构建（Debug 配置加 `-O`），CPU_ONLY。测试时热状态始终是 nominal，没有开低电量模式。模型用无状态 INT8 包。

集成代码在 Vime 的 `feat/chinese-language-model` 分支上，还没有合并。做法如下：

- 候选由 Rime 产生。模型只重排前 8 个完整转换，打分用的是光标前那句话之后接上各候选的简体文本。
- Rime 的原顺序作为先验，每往后一位扣 1.0 对数概率。
- 候选栏最多等打分 60 ms，超时就按 Rime 的顺序显示。模型还没加载完时，当前列表立即显示，模型留给后续输入。
- 用户学过的词、部分转换和排除词，模型都不会移动。
- 扩展里同一时间只加载中文模型和日文模型中的一个。

**扩展进程内**：XCUITest 在已安装的键盘上真实点击，每轮 5 分钟，约每秒 1.2 次。开模型的一轮点击 361 次，上屏 36 个词或短语；关模型的一轮按 Rime 原顺序，扩展内计时 309 次。下表的计时都在扩展进程里测得。p95 取各计时窗口 p95 的最大值，每个窗口是最近 256 次调用。

| 指标 | 开模型 | 关模型 |
| --- | ---: | ---: |
| 按键 → 候选可点（`inputToCandidateInteractive`）平均 / p95 / 最大 | 26.1 / 45.0 / 49.7 ms | 20.3 / 26.1 / 27.4 ms |
| 等待打分（`chineseRankingWait`）平均 / p95 / 最大 | 13.9 / 36.4 / 40.9 ms | — |
| 模型打分（`lmCandidateScoring`）平均 / p95 / 最大 | 13.2 / 36.3 / 40.8 ms | — |
| 按键到上字（`touchUpToType`）平均 / p95 | 0.40 / 0.93 ms | 0.41 / 0.83 ms |
| 物理内存中位数 / 最大；进程峰值 | 20.0 / 29.5；29.9 MiB | 24.3 / 25.3；25.7 MiB |
| 扩展内加载模型 | 253 ms（一次） | — |
| 可打分 / 按时打分 / 顺序有变 | 222 / 221 / 173 | — |

- 开模型后，按键到候选可点的 p95 多了约 19 ms，最大值 49.7 ms，仍在 60 ms 的等待上限以内。222 次里只有 1 次没用上打分结果，原因可能是超时，也可能是模型还没加载完，那一次显示的是 Rime 原顺序。
- 173/221 指前 8 个候选里有顺序变化，不等于首选变了。
- 扩展内打分比测试宿主慢好几倍：宿主里平均 2.7 ms，扩展里 13.2 ms。原因还没确认，可能是真实文档给的左文更长（最多 64 字，在句号、感叹号、问号或换行处截断），也可能是扩展的 CPU 调度不同。
- 扩展内存峰值 29.9 MiB，比关模型多 4.2 MiB。两轮物理内存的中位数反而是开模型更低，这是两次运行之间的差异，不能当作模型的内存成本。

**测试宿主内的端到端重排**：24 个“拼音 + 前文”用例逐键输入，每次按键都会依次经过 Rime、取前 8 个候选、模型打分。共跑 3 遍，下面取第 2、3 遍：428 次按键，300 次打分，平均每次打 7.1 个候选。Rime 每键 p50 0.09 ms，p95 0.31 ms。模型打分 p50 1.9–2.0 ms，p95 9.2–9.8 ms，最大 14.8 ms。Rime 加打分合计 p95 9.0 ms。没有打分超过 60 ms，也没有失败。逐例结果里能看到模型按前文调整顺序，例如前文“数学”加 `gongshi` 时，“公式”排到了“公示”前面。

**分块 KV 包（真机）**：首次加载 236–280 ms，再次加载 1.3 ms。加载后占 37.6 MiB，预测后约 48.5 MiB。各长度单次调用的 p50 如下：

| 每次调用的 token 数 | p50 |
| --- | ---: |
| 1 | 2.4–2.9 ms |
| 32 | 4.0 ms |
| 64 | 5.2–5.3 ms |
| 128 | 7.5–7.6 ms |

重排 3–6 个短候选时，KV 路径 p50 13.5–14.0 ms，无状态联合打分 p50 约 9.0 ms。原因是每次调用要搬两份约 1.8 MB 的缓存，这笔开销超过了它省下的计算。因此键盘用无状态包。测试进程的峰值约 119 MiB，来自测试框架没有在调用之间释放对象，不是模型的常驻占用。

模拟器（iPhone 17,2，Debug 构建）只用来确认流程能跑通，数字不作参考。

### 上线前还要补的测量

- 中文联想：键盘里还没实现，没有数据。
- 扩展内打分比宿主慢 4–5 倍：需要定位原因。可以固定左文长度，在宿主和扩展各测一次。
- 内存压力下的行为、冷启动和耗电。
